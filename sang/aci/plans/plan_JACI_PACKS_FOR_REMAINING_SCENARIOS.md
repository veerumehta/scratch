## Template

`aml_investigation_core` is the pattern to copy: `pack_manifest.yaml` with a `conductor_pipeline`
(investigation loop, a human checkpoint, a narrative step), `evidence_tools.yaml` plus fixtures,
`policies/`, `mode_tuning/` (replacing `prompts/<scenario>/`), `schemas/` generated by
`scripts/export_pack_schemas.py`, and metrics where a deterministic check exists. Publish with
`scripts/publish_packs_to_plato.py`, one tenant per pack (`PACK_TENANTS`).

Each new pack:
- starts at `pack_version` 0.1.0 and `certification_status: draft`; a later change bumps it, with your OK,
- carries the scenario's tuning as data (`mode_tuning/*.md`), moved from `prompts/`, not rewritten,
- gets its rule tests in-process through a `tests/scenarios/<scenario>/pack_assessment.py` helper, as DSCR does,
- gets a Plato-run integration test marked `requires_plato`, and a page that runs only on Plato, as DSCR does.

## Solution blueprints: how the packs of one domain compose

Plato has blueprints (`PUT /blueprints/{id}/{version}`, `activate_blueprint`, client `put_blueprint`):
a named set of published packs that make one solution, each with a version range, resolved to the newest
live version at activation, and the exact versions cited by a run record. A blueprint does not compose
the packs; it names them. Read from `jazzx_sdk/pack/blueprint.py` as checked out, the rules are:

- members have a role: `policy`, `assistant`, `core` (a shared domain pack the policy builds on) or
  `reference` (an imported job set);
- **exactly one policy member, and at most one of each other role**;
- members resolve inside one tenant's published packs;
- an assistant's `policy_pack_id` must name the blueprint's policy pack.

jaci defines no blueprint today. What that means for the domains here:

| Domain | Blueprint shape that fits the rules | Does not fit |
|---|---|---|
| Commercial lending | one blueprint per policy pack: `dscr` = acra-dscr-policy (+ core, + reference for the Acra taxonomy), `cre` = cre-underwriting-core, `ci` = ci-spread-core | one "commercial lending" blueprint naming DSCR, CRE, C&I and the CL packs together (four policy packs) |
| Financial crimes | `aml` = aml-investigation-core; `kyc` = the KYC pack, with an assistant member if one is added | one blueprint naming AML and both KYC packs |
| Clinical intake | `clinical-intake` = policy pack + its assistant pack | n/a |

So a domain-wide composition ("one solution for commercial lending") cannot be expressed as one
blueprint as the rules stand, and the five commercial-lending packs also live in different tenants
(`acra-lending`, `mesa-verde`, `workshop-bank`), which a blueprint cannot span. Two ways forward:

- (a) per-pack blueprints now, grouped by `domain` and `segment` in the blueprint metadata, which is
  what the manifests already carry; no japes change;
- (b) ask japes for a multi-policy blueprint (several policy members, or a blueprint of blueprints), then
  compose per domain. That is japes work; I would send the request to `opus-xrepo`, not build around it.

I would start with (a), and publish each blueprint with the pack through `publish_packs_to_plato.py`, so
a blueprint exists for every pack from its first publish.

not a rename. So: the published ids stay (`acra-dscr-policy`, `aml-investigation-core`,

## Portfolio monitoring: a book-level monitor

Decided: it is a collection of loans, so the pack's subject is the book, not a loan.
- The case input is a book (a set of loan references with their current figures), `subject_field` the
  book id; the output is the review items and their statuses, which is what `monitoring.py` and the
  demo contract (`scenario_contract.py`) already compute.
- The computation is deterministic, so most of it is `metrics.yaml` and `policies/` (thresholds are
  `pending configuration` until a source gives them), and the LLM part is the narrative per flagged loan.
- The human step is the reviewer's answer on the flagged items, as a checkpoint at the end of the book run.
- To confirm against Plato: whether one run over a book of many loans fits a case run's input and journal,
  or the book is a subject of many loan runs. I would test it with the demo book before writing the pack.

## Threat intel: a showcase for an external team

Decided: it will be pitched to an external threat-intel team, so a basic working solution is the goal,
packs where none exists, and a worked example of using it through `jazzx_plato_client`. Today only
`handler.py` (an SDK `AutomationHandler` composing `DiscoveryExpert`) and its schemas exist, with no
fixtures, no gold cases and no page.

What the showcase needs:
1. **A pack, `threat-intel-core`:** an investigation-shaped conductor over a finding (a report, an
   indicator set or an advisory): triage, relevance to the customer's environment, and a proposed update
   (watchlist, rule, or advisory note), with a human checkpoint before anything is proposed to a
   downstream system. Typology-style knowledge (source credibility, indicator types, severity) lives in
   `mode_tuning/`, and the closed vocabularies in the schemas. Sources are fixtures, since real feeds
   are the prospect's to connect.
2. **A scanned-source surface:** the scheduled scan has no case, so the showcase runs a scan as a batch
   of case runs: one run per finding the scan surfaces. Whether Plato later grows a scheduled-run
   surface does not change the pack.
3. **A client walkthrough:** a script and a page (`scripts/threat_intel_demo.py` and a Streamlit page)
   that publish the pack, submit findings, follow the runs, answer the checkpoint and read the
   `chain`, using only `jazzx_plato_client`. This is what the external team would copy.
4. **Gold cases:** a small invented set (a relevant advisory, a duplicate, an irrelevant noisy one),
   written by me but each one asked about before it is added.
5. **No real customer or live feed data** in the repo.

Unknown until a first pass: whether the existing `DiscoveryExpert` output maps onto a Plato step kind,
or the pack runs the generic `investigation` kind with the scan's findings as evidence. I would find
this out in the first day of that work, and report it before building further.

## Per-pack steps

1. Inventory the scenario: modes, tools, schemas, policies, skills in `prompts/`, gold cases.
2. Write the pack beside the in-process code: manifest, evidence tools and fixtures, policies, `mode_tuning/`.
3. Generate schemas; run the offline pre-publish gate (`check_pack_archive`, `conductor_problems`); write the pack's blueprint.
4. Publish the pack and its blueprint to the scratch tenant, run the gold cases through the route, compare with the in-process
   result. Differences are reported, not smoothed over (japes findings go to opus-xrepo).
5. Move the page to "Plato only" and delete the in-process conductor and its SDK imports, keeping the
   in-process rule tests.
6. Changelog line; a `done_` writeup when the scenario is finished.

Done for a scenario means its `scenarios/<name>/` imports no `jazzx_sdk`, apart from schemas the pack
also generates from.

## Constraints

- Gold cases and fixtures: ask before each change, and report the same defect elsewhere rather than
  folding it in (`feedback_fixture_changes_per_case`).
- No invented numbers in policies or thresholds: `pending configuration`, as in the workshop bank packs.
- No version bump of jaci or a pack without asking; a new pack's 0.1.0 is not a bump. Bump only when
  the change is material.
- Never push; commit with explicit paths.
- The real Acra borrower data is out of bounds for this work, as everywhere.
