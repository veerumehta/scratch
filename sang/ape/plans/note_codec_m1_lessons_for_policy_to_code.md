# What CODEC's Milestone 1 report tells us about our policy-to-code work

Author: Virendra Mehta
Source: Notion, "CODEC - Milestone 1: PULTE Development Benchmark Report" (report date 2026-10-21, evidence cut-off Oct 21). Read with `Acra_JTBD_and_Code_Generation_Assessment.md` and `plan_JAPES_2_9_0_JOB_WRITER_COVERAGE_AND_CODABILITY.md`.

## TLDR

CODEC is the mortgage team's reader-plus-generated-checks system: an AI reader extracts a loan file once into a versioned ontology snapshot, then 115 Python evaluators generated from 115 JTBDs decide the conditions. On seven Pulte development loans it matched 155 of 172 SME end-state conditions (90.1%) against MACER's 132 (76.7%), at a third of the cost ($2.07 vs $6.26 per loan) and with far better repeatability (95.3% of rows identical across three runs vs 77.3%). The report is a benchmark, not a design doc, and it does not describe the generator's prompts or any intermediate representation, so what we can take from it is the architecture around the generated code and the evaluation discipline, not the generation step itself.

Six things in it bear directly on our SDK work, and three of them change what we had planned.

1. They generate code for every JTBD and let the run say what it could not decide (`GAP_OF_INPUT` as an execution status, kept apart from the verdict). We gate on the writer's one-shot "which checks are computable" and write code for half the jobs. Their way is better and simpler: write code for every job, make the missing field a run-time fact, and derive the schema backlog from runs rather than from the writer's guess. This replaces most of W4.
2. Their evaluators run in tiers over a dependency DAG and each one reads the findings of the ones before it. That is the engine piece our W3 and W5 (`derived:<rule_id>` reads) are missing, and they have shown it works at 115 rules.
3. Their checks are hybrid: a shared text helper (a small model) answers the minority of sub-checks that code cannot, inside the rule, bounded and failing safe. That is a third option beside "code it" and "leave it to a reviewer" for our partial checks.
4. They put the data model first and say so: "a new domain first needs a well-designed, LLM-friendly data model. Once that exists, generating the checks is a straightforward, repeatable process." Their snapshot has 252 tables and 5,727 columns, with 184 tables and 1,796 attributes read by evaluators. Our Acra template offers the writer 47 fields. This is our decision 1 (bind to the canonical object schema), and the report is the evidence for making it now.
5. Their evaluation is the part we lack entirely: SME-cleared conditions as answer keys per loan and per batch, an LLM judge with three votes, repeat runs with Cohen's kappa, strict precision and duplicate rates reported alongside recall, pinned build hashes and key checksums, and a fix-loop audit that classifies every miss as "SME conflict, listed for review" or "extraction or rule gap". We measure job counts and coded share; we have no answer key for Acra.
6. Their weak spots are a warning for us. Strict precision is 10.8 to 15.6% (most open conditions match no SME row), exact duplicates within a stage are 8.6% against MACER's 1.4%, 83 of 115 checks carry hand fixes, calculations are the weakest area (income 27 of 70, 38.6%), and nothing is held out yet. Per-JTBD generation over-asks and duplicates unless something above the rule level merges and suppresses; aggregations and derived figures are where generated code fails first. Both match what we saw in the Acra sets.

## What to change in our plan

W4 becomes smaller and runs later. Instead of a model pass that classifies each check before code is written, write code for every job whose checks name at least one field, keep the writer's computability only as a hint in the prompt ("encode what the fields decide; return unknown for what they do not"), and read the schema backlog off the run: a rule that returns `unknown('lowest_listing_price')` on every case has told us the field it needs, in code, with no second model call. The per-check classification survives only as the `left to reviewer` label (W5), and even that can be read from the rule's own dict return. The two gates that stay are the static check and the cases.

W3 and W5 get their engine piece named. CODEC's `FindingContext` is the shape: run rules in dependency tiers, pass each rule the findings of the rules it names, and let a job read `derived:<rule_id>` as that rule's verdict plus its reported values. The slice-1 plan already recorded that `derivation_backlog` is not a runtime path; this is the plan for the runtime path, and it is small once rules declare what they read.

Hybrid rules for the residue. Add a third outcome for a check the fields do not fully decide: a bounded text call over the cited evidence, inside the rule, with the question, the quote it accepted and the answer in the trace, failing to `unknown` on any doubt. CODEC keeps this to a minority of checks and says it "fails safe"; we should cap it the same way (one call per residue, no retries, quote validation as in their Phase D). This is what lets a document-presence verification ("an executed W-8 BEN is on file") become a rule before the document registry exposes presence fields.

Run health before rules. A fail-closed gate on the case record (required fields by program, document classes present, health codes) before any rule runs, with the run rejected downstream when CRITICAL. We have the pieces (`required_classes` in the conductor, `_unstated_facts` in assessment) but not the gate.

An answer key for Acra. Everything above is unmeasurable without one. The cheapest version: for the Acra sample loans we already have fixtures for, an underwriter-cleared list of conditions per loan (and the handful of derived figures: DSCR, qualifying rent, governing CLTV), scored by the same definitions CODEC uses so the two programs can be compared on one scale: end-state match, strict precision, duplicates, repeat consistency with kappa, cost per loan. Three repeats per build, with the slice-1 noise rule. The hand-built JTBD set stays the reference for job coverage; it is not an answer key for code.

Regeneration discipline. Keep every hand fix as a correction case in the pack (we have `correction_cases`), regenerate without the fixes, and diff rule verdicts row by row on the answer key. CODEC's wave-1 result (a no-edit regeneration matched the hand-tuned score of 151.4) is the standard: a lesson that does not survive regeneration is not in the generator yet.

## What not to copy

CODEC's generator is not described, and 83 of 115 of its checks were hand-fixed on the seven loans it is scored on; the report itself lists "none is held out" as a risk and asks for a freeze before the held-out run. The 90.1% is a development score. Its precision and duplicate numbers show that per-JTBD rules without a merge layer over-ask, which is the same lesson as our cross-section duplicates. And its calculations are weak where ours will be weak too: aggregations, income, anything derived across tables. We should not expect the generated-code path to carry the DSCR calculation or the governing-CLTV composition without the DAG and the derived-field work; that is W3, and CODEC's income numbers are the reason to do it carefully.

## Glossary from the report

CODEC: the reader plus generated Python checks system (Codec Suite: Data Extractor, Code Generator, Reasoner, Gap Analyst, control plane). MACER: the incumbent agentic verifier, whose models re-check each JTBD against the documents on every run. Pulte: the lender whose seven development loans and SME-cleared conditions are the benchmark. Answer key: SME-cleared conditions, end-state (172 rows), per batch, and calculations (178 rows). Batch B1 to B3: document arrival stages. Fresh run vs cached read: full re-extraction vs replay of saved reads. Phases A to D: evaluators, verdict pick, bounded document search, grounding (off in M1). M2: the held-out validation they recommend next.
