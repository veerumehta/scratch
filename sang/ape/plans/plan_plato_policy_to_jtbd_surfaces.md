## (a) Adoption: job set to guide units, no model call

Inputs (three, all text so no server path is read): the guide as markdown text (upload or pasted), the mapping document (`{edition, links:[...]}` JSON or YAML), and a draft pack id whose jobs are adopted. Optional: the `MarkdownGuide` patterns (chapter, topic, edition) as three text fields; default is the Selling Guide's.

SDK gap 1 (for sonnet-runtime): `read_markdown_guide` takes a `Path`. A route holds upload text, so it must write a temp file (the extract route does this already for uploads) or the SDK adds `parse_markdown_guide(text)`. Recommend the SDK verb; the route should not own temp-file handling.
SDK gap 2: no verb that runs "draft pack + corpus + mapping -> adopted policies written back to the draft" (the route would otherwise load policies, call adopt, and serialize them to the draft's policy files itself, which is logic). Ask: `adopt_into_pack(policies, corpus, mapping) -> (policies, AdoptReport)` plus the serializer the draft store already uses for policy files. [U] which function the draft write path uses to serialize rule edits (`PUT packs/drafts/{id}` writes files; the rule-level writer was not traced).

Routes (thin):
- `POST /packs/drafts/{pack_id}/adoption/preview` (multipart: guide, mapping, patterns): author gate (`_refuse_unless_author` style), no write; returns `AdoptReport` plus counts by status and the unit list (id, citation, edition). Pure, cheap, lets a person fix unresolved ids before writing.
- `POST /packs/drafts/{pack_id}/adoption` (same body): the same call, then writes the adopted policies into the draft. Idempotent by the SDK's row key (unit, check, source).
- `PUT /packs/drafts/{pack_id}/links/review` body `{job, unit, check?, source, reviewer?, date?}`: flips one link to reviewed. Reviewer comes from the authenticated identity (`acting_user_id`), date from the server clock; both are never taken from the caller so the attribution is true. [U] whether a SDK verb for a single-link review exists (the pure review transform was not found in `source_links.py`; "a review replaces the row it confirms" is only reachable by adopting a link with status reviewed). Ask: `review_link(policies, job, unit, check, source, reviewer, date)`.
- Every route: strict-posture gate with optional params checked after it, a client method in `jazzx_plato_client/_authoring.py`, entries in `test_plato_route_gates.py` and `test_plato_client_routes.py` (page route in the exemption list), no caller string reaching a path or pattern (the three patterns are compiled regexes: wrap `re.error` as 422; [U] ReDoS bound on a caller pattern, ask the SDK to cap pattern length or compile with a timeout).

Where the result lands, and the Pulte size problem: the adopted result is the job rules with links, written into the draft's policy files, so it fits a draft like any job set. The GUIDE ITSELF (4.9 MB for the Pulte policies directory) does not fit a draft file at 1 MiB, and splitting it per chapter would run into 500 files only if topics are split finer than chapters. Options:
1. Do not store the guide in the draft. Adoption only needs the guide at write time (units, spans). Each link already carries `ref` (topic id, edition, byte start and end) and the citation. Cost: a reviewer cannot read the unit text in Plato, and spans point into a file Plato does not keep. Smallest, recommended for the first cut.
2. Store the guide split per chapter in the draft (about N chapters, each under 1 MiB, [U] Pulte chapter count and the largest chapter size; must be checked on the real directory without opening borrower PDFs, which this is not). Spans then need chapter-relative offsets: an SDK change to `SourceRef`.
3. Store it as one blob outside the draft through the published archive path (pack archive route `packs/{id}/{version}/archive`, [U] its size limit not read) or `fabric.blob`. A reviewer reads unit text from the blob; the draft holds only the blob id. Needs a Plato route and an SDK verb for the blob read by span. Largest.
Raising `PLATO_DRAFT_FILE_MAX_BYTES` to fit 4.9 MB is possible (the env is read per call) but is a deployment change that also raises the near-cap warning threshold for every file; not recommended as the design.
Decision for the user and sonnet-runtime: option 1 now, option 3 if reviewers must read unit text in Plato.

Page: new `adoption.html` (nav entry under Solution or on the Packs page, "Adopt a job set"): three inputs, Preview, a result panel with unresolved (job, unit, reason) and edition mismatches (job, unit, link edition, unit edition) as tables, then Write to draft. The existing links display: the Coverage page already shows "Check links" counts and the Solution page "N model links not reviewed" (v2.6.7, [V] per restart file, not browser-checked). Add to the Coverage clause table a per-link detail drawer: status badge declared | unreviewed | reviewed, reviewer and date, edition and unit edition with a mismatch flag, quote and p for unreviewed. Link detail rows live only in each job's `check_links` metadata ([V] per restart file); a per-link API field is on the 2.6.8 carried list, and this drawer needs it, so the two should be one piece. The reviewer flip is a button on an unreviewed row calling the review route above.

Tests (node first, via `tests/test_plato_pages_run.py::_DOM` and `tests/page_scripts.py`, never a regex): the preview table renders unresolved and mismatch rows; Write is disabled until a preview ran; the review button calls `el.onclick()`; reviewed rows show reviewer and date. Route tests with a stub that matches the production shape (the draft store, not a mock returning None where the real store returns a row).
Size: preview + write + review routes about 150 lines, client methods about 40, page about 250, tests about 250 (estimates, [U]). Risk: medium (draft writes, regex input, the guide-size decision). Order: 3 of 4. Plato 0.2.8 if bumped.

## (b) Ontology source stamp and Hub refresh

Exists: `OntologySource` (`current()`, `refresh(kh, force=)` never raises, returns `RefreshOutcome` adopted | unchanged | rejected | unavailable), `OntologyStamp` (source_status seed | hub, source_id, source_version, source_sha256, fetched_at, hub_id, hub_version, source_file, scope, entities_read), `stamped_catalog` writes `x-provenance`, manifest `catalog_source:` read by `manifest_loader.catalog_source_config()` [V]. `KnowledgeHubClient.read_ontology` and `resolve_current_ontology` exist [V]. Plato wiring carries a KH client only when `resolve_knowledge_hub_url` finds a URL (`plato/wiring/default.py:330`) [V]; [U] how a route reaches that client.

Behavior to specify (the SDK is silent on it): `OntologySource` holds the document in memory and never writes a draft. A refresh that differs only changes its in-memory document and stamp; nothing publishes it. So for a draft: the draft's `catalog.schema.json` keeps its own `x-provenance` until a person acts. Plan: refresh returns the outcome and a diff of the Hub document against the draft's catalog (`catalogs/references/.../compare` and `catalog_adopt.adopt` already compare and conflict-report; reuse them), and a separate "Apply to draft" action writes `stamped_catalog(document, stamp)` into the draft. A field in the draft that differs answers 409 with both sides, as `catalog/adopt` does. Never overwrite silently.
SDK asks: (1) a verb `catalog_status(draft_files) -> OntologyStamp` (so the route does not parse `x-provenance` itself); (2) a verb `refresh_into_draft_proposal(source, kh, draft_catalog) -> {outcome, diff, stamped_document}`; (3) confirm a source object per pack is cached per process or built per request (`OntologySource` has a TTL clock and an asyncio lock that only help if it lives across requests; [U] not decided).

Routes: `GET /packs/drafts/{id}/catalog/source` (stamp, `catalog_source` config, `confirmed`), `POST /packs/drafts/{id}/catalog/source/refresh` (author gate, `force` optional; returns outcome and diff, writes nothing), `POST /packs/drafts/{id}/catalog/source/apply` (author gate, 409 on conflict). Published versions show their stamp read-only via the existing describe route.
Page: `ontology.html` header block "Source: hub | seed", id, version, sha256 (first 12 characters, full on hover), fetched_at; a "Refresh from Hub" button (hidden without author rights, disabled when no KH URL is configured, the same visibility rule the page already uses for write controls [V info.py:406]); outcome text; a diff table; "Apply to draft" with the conflict list. Neutral wording, no loan terms.
Tests: node: stamp block for seed and hub, button hidden for a reader, outcome states unchanged/rejected/unavailable each render a message, apply shows 409 conflicts. Route tests with a KH stub that returns `None` for a missing ontology (production does, `read_ontology` returns Optional [V]).
Size: about 90 lines of routes, 30 client, 80 page, 150 tests [U]. Risk: low-medium (outbound Hub call; SSRF is not a concern as the URL is the configured KH). Order: 2 of 4. Plato 0.2.8 if bumped.

## (c) Export lint and the export profile

Exists [V]: `GET packs/drafts/{id}/jtbdset/lint?profile=` and `GET packs/{id}/{version}/jtbdset/lint` return `{profile, errors, findings}`; `CHECKS` includes possible-dependency-cycle, possible-cross-section-dependency (warnings), metric-key-shared (warning) and metric-key-owned-twice (error). Nothing in `plato/static/*.html` calls the lint route (only `packs.html` downloads the JTBDSet). `ExportProfile` fields: name, field_caps, statuses, calculation_context_required, requirement_style (plain | guide), fixed_blocks, reference_cues, severity (check name to error | warning, validated against `CHECKS`). Profiles are YAML files at `export_profiles/<name>.yaml` in the pack ([V] `EXPORT_PROFILES_DIR`).
Correction to the brief: `metrics_key` is NOT an `ExportProfile` field. It is a field of the pack's `JtbdTemplate` (`jtbd.py:170`, the pack's JTBD template YAML, found by `pack/lint.py:591`). Editing it is a template edit, and it changes how every writer and reader names the metrics, so it is not a per-consumer export setting. Plan: show it read-only on the lint page, edit it through the draft file editor, and ask sonnet-runtime whether it should move to the profile (their call).

Editing a profile: no new route is strictly needed, a profile is a draft file. The existing draft file write (`PUT packs/drafts/{id}`, [V] route exists, body shape [U]) can carry it. A thin helper route is better so the page edits fields, not YAML, and a bad value is a 422 with the pydantic message: `GET/PUT packs/drafts/{id}/export-profiles/{name}`. The PUT validates with `load_export_profile`/`ExportProfile.model_validate` (SDK, so no new logic in Plato), writes the file. SDK asks: a `dump_export_profile(profile) -> yaml` so a round trip does not reorder or drop comments ([U] whether comments in an existing profile survive; assume not and say so on the page), and `reference_cues` schema export for the editor (ReferenceCues fields [U] not read).
Page: a "Lint" tab on `packs.html` or a new `lint.html` (preferred: `packs.html` is 2163 lines): profile picker, findings table (code, severity, job, message), grouped by severity, counts, a severity-override control per code writing the profile's `severity` map, `requirement_style` select, `reference_cues` edit as a list of cue strings per class, a Re-run button. Findings that are only "possible-*" are labeled as warnings a person decides, not blockers.
Tests: node: findings render by severity; the four new codes render with their text; a severity override posts the map and the table re-sorts; an invalid profile shows the 422 text. Route tests: the PUT refuses an unknown check name (`severity` validator [V]) and a non-positive `field_caps`.
Size: routes 60, client 20, page 220, tests 180 [U]. Risk: low (lint is read-only; profile write is a validated file). Order: 1 of 4 (smallest, no new SDK verb strictly required). Plato 0.2.8 if bumped.

## (d) Guide-scale extraction through /authoring/extract

What exists [V]:
- `POST authoring/extract/{pack}/runs` takes `documents: list[UploadFile]` (multipart), each converted to text with `convert_document` (cap `MAX_DOCUMENT_BYTES` 25 MiB each), plus `policy_id`, `representation` (jtbd default), `model`, `step_models`, `references`, `flex_fallback_after`, `budget_usd` (positive float, 422 otherwise). The documents reach `SectionSegmenter` as `(name, text)` pairs.
- Batched planning exists inside `SectionSegmenter.segment` (`jtbd.py` `_batches`, `batch_by_group`, `plan_limits.PLAN_MAX_INPUT_TOKENS` 60,000, one batch when everything fits, otherwise batches cut between chapters, a second pass for unplaced units, `PlanTooLarge` when one unit alone is over the window). Chapter grouping comes from `chapter_key_of_text` on the text.
- The per-run ceiling: `CallMeter(limit_usd=run.budget_usd)`; a failed run at its ceiling gets "stopped at its ceiling of N USD" in `run.error` (`policy_extract_api.py:343,505`). Job runs and alignment runs take `budget_usd` too.
- Progress: `ExtractionRun` carries stage, segments, segments_total, proposals, calls, cost (from `_progress_fields`) and `GET runs/{id}/stream` streams it.

What is missing / differs from the brief:
1. A guide is taken as one markdown FILE converted to text, NOT as a `StructuredCorpus`. `read_markdown_guide`, `read_structured_corpus` and `plan_batches` (structured_corpus.py) are not called by the route or by `SectionSegmenter` [V by grep]. The planner that runs is `SectionSegmenter`'s own, driven by text and `chapter_key_of_text`. So the two planners are separate code paths: the corpus one (topic ids, editions, byte spans) is only reachable from the adopt side. For a guide with topic ids and editions kept on the extracted jobs, extraction needs to read the guide as a corpus. SDK ask: `SectionSegmenter` (or a new segmenter) takes a `StructuredCorpus` and uses `plan_batches`, so unit ids and spans survive into `citations`/`check_links`. [U] whether `SectionSegmenter` already preserves topic ids from heading text.
2. Progress is per segment (`Progress.start(total)` restarts counts per pass), not per plan batch. I found no batch index, batch count or per-batch cost field in `ExtractionRun`. [U] whether `on_stage` labels name the batch (the stage string was not traced in `SectionSegmenter`). SDK ask: a `batches_done / batches_total` pair and per-batch cost in `_progress_fields`, and a stage label per plan batch.
3. The ceiling stops the run when exceeded (an exception after the call that crossed it, `cost_tracker` raises "Budget exceeded" [V line 138]); it is not a pre-flight estimate. For a guide-scale run the page should show a pre-flight estimate (tokens from `estimate_tokens`, batch count from the planner) before submit. SDK ask: `plan_estimate(documents) -> {batches, input_tokens}` with no model call. [U] whether partial proposals survive a ceiling stop (the code sets `run.segments` on failure; proposals not checked).
4. Upload cap: 25 MiB per document is fine for 4.9 MB; [U] Pulte's guide is a directory of files, so it is many uploads: two uploads with the same filename are refused (422), and file order sets the plan order [U].

Plato work (smaller than the others because the route exists): `extraction.html` already posts to `authoring/extract/{pack}/runs` ([V] ontology.html:361 does; extraction.html [U] not read for `budget_usd`). Add a budget_usd field, a pre-flight estimate (when the SDK verb exists), and per-batch progress rows (when the SDK exposes them), and the "stopped at its ceiling" message as a distinct state with the proposals so far. Without the SDK asks the page can only add the budget field and the ceiling message.
Tests: node: the budget field posts `budget_usd`, a non-positive value is refused client-side with the server's message, the ceiling state renders. Route: already covered by `tests/test_extract_budget.py` [V file exists, content not read].
Size: budget field and message 60 page lines, 40 tests, then 100 more once the SDK verbs land [U]. Risk: low for the budget part (spend is the user's: a run is a provider call and needs the user's own approval, per CLAUDE.md; the page must show the ceiling clearly and never default it). Order: 4 of 4 for the full item; the budget-field slice can go first with (c). Plato 0.2.8 if bumped.
