Repo: /Users/sangit/src/policy-workbench (PW), branch JAPES_V2. SDK: japes, package `jazzx_sdk`.
Model: /Users/sangit/src/jazzx-assistant commit 2882dc8 (git-rev pin through `[tool.uv.sources]`, thin adapters,

Rules carried over: SDK-first (logic lives in the SDK, PW keeps adapters), tolerant first, one logical change per
commit, PW's CLAUDE.md protected features are invariants (read the engineering note before touching an area).

## Findings that shape the order

- japes requires Python >=3.12 (poetry `python = ">=3.12,<4.0"`); PW was 3.11 (pyproject, Dockerfile, CI). Slice 1 moves PW to 3.12.
- japes' git dependency graph includes private repos (client-api: kernel-client, knowledge-hub-client) and path-sourced
  subpackages (jazzx_eval_contracts, jazzx_plato_client). jazzx-assistant's uv.lock shows uv resolves them; pip would not
  be trusted to. So installs move from pip to uv, with a GitHub token as a build secret (Dockerfile) and a git
  `insteadOf` rewrite (CI).
- The `japes[mlflow]` extra installs full `mlflow`; PW deliberately ships `mlflow-skinny` (CLAUDE.md: do not restore plain
  mlflow). Slices 1-3 need only `mlflow.flush_trace_async_logging`, so PW depends on bare `japes`. A later slice that needs
  full mlflow (SDK MlflowReporter, prompt optimizers) must reopen this.
- japes core pulls a lot (azure-identity, sqlmodel, asyncpg, openai-agents>=0.22, the client packages). Image size growth is
  UNMEASURED; measure after the first build.
- SDK cost model has one cache-write rate, no 5m/1h split; PW's usage readers produce both.
