[DEFECT] jazzx_sdk/agents/interactive/recorder.py:96 :: close-lock-popped-while-awaited -- The `finally` drops the session's lock whenever `not lock.locked()`. That is also true while another close is still queued on the lock, and the `pop` does not check that the entry is still this lock. So "closes of one session in this process take turns" does not hold.
Trigger: close A's `put_trace` or `put_decision` raises. Close B is waiting on lock L. `asyncio.Lock.release()` clears `_locked` before B resumes, so A's `finally` sees it unlocked and pops L. Close C arrives, `setdefault` makes a fresh lock L2, and C runs while B runs. Both find no Trace (or no Decision) and both write one. When B finishes it also pops L2 while C still holds it, which repeats the problem for the next close. The `TODO(concurrent-close-writes-twice)` says only replicas still race, and that part of the deferral does not hold. Fix: pop only when `self._closing.get(session_key) is lock` and nothing is queued (e.g. a waiter count), not on `locked()`.
IMPORTANCE: medium -- I traced it through `SessionRecorder.close`, the only entry point. Hitting it takes a failed canonical write plus three or more closes of one session in one process (e.g. a client retrying a 500). The result is a duplicate terminal Decision or Trace in the canonical store, with no error.
