[DEFECT] jazzx_sdk/pack/draft_db.py:279 :: discard-skips-draft-lock -- `discard` does not take the draft lock first. It deletes the file rows and then the draft row, while `write_file` and `delete_file` now lock the draft first and then the files, and the new comment claims the writers "queue in one order".
Trigger, on Postgres, with one author pressing Discard (`DELETE /packs/drafts/{pack_id}`, `packs.py:650-660`) while another saves an existing file:
- Deadlock: `write_file` holds the draft `FOR UPDATE` and wants that file row. `discard` has already deleted the file row and now waits on the draft row. Postgres aborts one of them with a deadlock error, which surfaces as a 5xx.
- Orphaned row: if the save is a new file instead, `write_file` inserts it after `discard`'s file delete has run, commits, and `discard` then removes the draft. That leaves a `PackDraftFileRow` with no draft. The next `open` whose seed has that path hits `uq_pack_draft_file_path`, is treated as a concurrent open, finds no draft and raises "was discarded while it was being opened". Opening the pack from that seed then fails every time until the row is removed by hand.
The fix is one `blocking_locked_first` on the draft at the top of `discard`, matching its two siblings.
IMPORTANCE: medium -- the only callers are Plato's draft routes (`write_file` via PUT, `discard` via DELETE, `delete_file` via DELETE with `rel_path`), and nothing outside the repo uses them. It needs two editors on one tenant's draft at the same moment on the Postgres backend (sqlite serializes writers). The deadlock is loud. The orphaned row persists and blocks opening, and only direct database access clears it.
