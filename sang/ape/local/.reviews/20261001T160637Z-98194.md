[DEFECT] plato/api/packs.py:158 :: persist-merges-replica-env -- `_persist_active_pack` builds the durable `PLATO_ACTIVE_PACK` value from this replica's `os.getenv` rather than from the stored value, so an activation on one replica deletes another replica's durable entry for a different pack, and the new retire guard then stops protecting that version.
Trigger: two replicas share one DB. Replica B activates `acme/other/2.0.0`, so the durable value is `acme/other/2.0.0`. Replica A booted earlier and its env has no entry for `other`. A then activates `acme/shared/1.0.0`. `with_active_pack(<A's env>, ...)` returns `acme/shared/1.0.0`, and `durable_settings_store(db).write` stores only that. B's activation is now gone from the store, so the next restart quietly reverts `other` to the newest version. Also, `_durably_active(db, "acme", "other")` returns None, so `DELETE /packs/other/2.0.0` on A succeeds while B is serving that version. Pins load only at boot (`plato/wiring/default.py:715`) and nothing resyncs them, so A's env stays stale until it restarts. The fix uses the same read this diff adds: merge against `(await durable_settings_store(db).read()).get(ACTIVE_PACK_ENV)` when `db` is set.
IMPORTANCE: high -- the activation is lost silently on restart and the caller cannot see it. Reachable from `POST /packs/{id}/{v}/activate` in any deployment with more than one replica and a DB. Single-replica deployments are unaffected because env and store agree there. Within plato, the only callers that write the durable value are the activate route (via this function) and `/config`. Whether any consumer outside this repo runs more than one replica: not established.
