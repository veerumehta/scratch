**[DEFECT] `jazzx_sdk/pack/store_db.py:167`** — the archive blob key is `packs/{pack_id}/{version}.zip` with no tenant and no digest, so a second tenant publishing the same `(pack_id, version)` overwrites the first tenant's bytes; `BlobStore.put` is a plain `path.write_bytes` on the default local backend. Trigger: tenant `acme` publishes `dscr-core` `0.1.0`, tenant `other` publishes its own edited `dscr-core` `0.1.0` — `acme`'s row is immutable and still points at `blob://packs/dscr-core/0.1.0.zip`, which now holds `other`'s tree, so `acme.materialize()` returns the wrong pack under `acme`'s own (now-wrong) `content_digest`. `materialize` at `:302` never re-hashes the fetched bytes, so nothing detects the substitution. `tests/test_pack_store.py:196-199` exercises exactly this flow but with byte-identical archives, so it passes. `store.py:65-66` states the property the key does not implement ("sharing the blob by digest"); `BlobStore.offload(dedup=True)` already spells the content-addressed key as `sha256/<hex>`.
IMPORTANCE: high — grep for `PackVersionStore` across the repo gives one non-test caller, `plato/models.py:49`, which only registers metadata; no plato router mounts publish yet. But japes is an SDK consumed by jaci/juno/plato, `publish` is public, and the bad key is written into `content_ref` on a table the module's whole premise is that it is immutable, so it is not fixable after rows exist. Azure `write_async` overwrite semantics I did not verify; local (the default) overwrites.

**[DEFECT] `jazzx_sdk/pack/store_db.py:71`** — `seq` is `autoincrement=True` on a non-primary-key column, which SQLAlchemy ignores, so every row gets `default=0`; the migration's `server_default="0"` matches. Verified: two publishes to a sqlite store give `[('0.1.0', 0), ('0.2.0', 0)]`. The tiebreak the column exists for therefore does nothing, and three comments claim it works — `:69-70`, `:73` (`"published_at orders them instead, with seq as a tiebreak"`), `get()` at `:243-244`, and `plato/migrations/versions/0003_pack_version.py:66-68`. IMPORTANCE: low — `published_at` comes from `datetime.now(timezone.utc)` and both backends keep microseconds, so two versions of one pack cannot actually collide across a DB round trip; the reachable damage is four comments asserting a guarantee that is absent. Deleting the column and the claims, or making it a real PK sequence, are both complete responses.
