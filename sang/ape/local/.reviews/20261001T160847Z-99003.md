[DEFECT] plato/api/packs.py:160 :: activation-merge-lost-update -- `_persist_active_pack` reads the stored `PLATO_ACTIVE_PACK`, merges one reference into it and writes the whole value back. Nothing ties the write to the value that was read, so when two activations overlap, the second write silently drops the first one's entry.
Trigger: replica A gets `POST /packs/shared/1.0.0/activate` and replica B gets `POST /packs/other/1.0.0/activate` (or the same replica gets both as two concurrent async requests). Both read the row while it still holds `acme/x/1`. A writes `acme/x/1,acme/shared/1.0.0`, then B writes `acme/x/1,acme/other/1.0.0`. Both requests return 200 and both audit rows say "promote", but after its next restart replica A serves `shared` on the newest version instead of the one activated. The route docstring's "(not atomic)" at :697 covers the If-Match check. It does not cover losing another pack's entry. `DbSettingsStore.write` (`jazzx_sdk/server/settings_store_db.py:141`) has no compare-and-set, so the caller cannot close this.
IMPORTANCE: medium -- The only path in is the author-gated activate route (`_refuse_unless_author`); I found no other caller of `_persist_active_pack`. It needs two activations inside one read-to-write window. The damage is silent: the lost activation looks persisted and reverts only at the next restart.
