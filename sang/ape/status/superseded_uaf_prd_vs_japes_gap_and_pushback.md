# Unified Assistant Framework PRD (Platform v2.0) — Gap Analysis vs. `japes`/`jazzx_sdk`, and Where We Push Back

**Sources.** Notion: *Unified Assistant Framework PRD — Platform v2.0* (fetched 2026-08-12). Code: `japes` working tree as of 2026-08-12 (HEAD `90475da`, v2.3.6+), 363 modules under `jazzx_sdk/` plus the shared `common/` package. Every code claim below was read in the tree and then re-verified by an independent adversarial pass; corrections from that pass are folded in.

**One-paragraph verdict.** The PRD is directionally right and we should build it — but it is written as if UAF starts from zero, and it doesn't. Roughly **65–70% of Phase 1 already exists in `jazzx_sdk`**, in several places in a *more* governed form than the PRD specifies. The genuine build is narrower and different from what the goal list implies: it is **(a) an assistant-id-addressed multi-tenant HTTP service, (b) per-skill action APIs with declared IO, (c) a hosted manifest store with versioning/rollback, (d) manifest-driven docs generation, (e) a skill record with inputs/outputs/visibility/version, (f) session lifecycle, (g) emitting a trace from the conversational path.** Meanwhile four of the PRD's design choices — *guardrails-as-skills*, *one common orchestrator with only the LLM configurable*, *manifest-as-single-artifact*, and *skills with no IO contract* — conflict with load-bearing decisions already made and tested in the SDK. Those four are the pushback.

### Critical-path summary (what to actually staff)

1. **Multi-tenant UAF service + manifest store** — assistant-id-addressed routes over `build_from_manifest`, per-assistant agent cache, manifest CRUD + **versioning + rollback**. (Goal 1/14/15.) *Medium.*
2. **Per-skill action APIs with a declared IO contract** — new `Skill` fields (`invokes`, `inputs`, `outputs`, `visibility`, `version`, `run_mode`) + generated routes off `GovernedRouter` + OpenAPI/docs from `describe()`. This is the Phase-1 product outcome and it is also the deepest change: it rewrites `_build_parent_tools`, which today exposes **every** skill as `(query: str) -> str`. (Goal 2/4/5/14.) *Large.*
3. **Process-engine invocation** — nothing in `japes` can start a BPMN process instance. This is an unresolved cross-team dependency (Kernel? new client?), not a japes delta, and it blocks the PRD's own async exemplar. *Name an owner this week.*
4. **Emit a trace from the conversational path** — `TraceStep`s for guardrail verdict, router decision, skill invocation, response; decide `CanonicalTrace`-as-format-of-record via `mlflow_bridge` vs. a third format. There is already an agent-side precedent for the span→`TraceStep` half (`agents/adjudication/tracing.py:26 adjudication_name_patterns()` feeding `spans_to_canonical_trace(name_patterns=...)`), so the mechanical work is cheaper than the *decision*. Cheap now, expensive later. (Goal 6/7/8/12.) *Medium.*
5. **Always-on guardrail floor + red-teaming gateway adapter** — the registry and execution exist; the floor and the gateway client do not. (Goal 8.) *Medium.*
6. **Session lifecycle** (`SessionStore` + TTL + sweeper + resume route) and **skill catalog seeding** (Jazz Assistant / Juno / PWB skills). *Small each, and both are on the acceptance path.*
7. **Identity adapters** — a **Keycloak/OIDC** client (genuinely absent), LOS access scope, require-context middleware at every service entry point, and a defined `PermissionScope` selector vocabulary for loans. Keto is already integrated in `common/core/keto/`, so scope that as wiring, not building. Do **not** put `OpaBundleStore` on this list: its methods raise `NotImplementedError` deliberately — the working OPA surface is `KnowledgeHubClient.get_policy_bundle/update_bundle/evaluate_policy/create_policy`, and bundle-upload is being superseded by canonical `Policy` on purpose (`fabric/opa/store.py:12-18`). *Medium.*

**On the PRD's premise.** *"Every new assistant needs its own code package on Azure"* is true of the three legacy assistants and **false as a description of the required work**. In this repo an assistant is already YAML — an `AssistantManifest` + a profile directory + a pack, bound at runtime by `build_from_manifest`, many-per-process via `ProfileRegistry`; `launcher.py:serve()` is one image in three shapes (`JAPES_RUN_MODE=queue|server|ui`). What is genuinely absent is a **hosted manifest store and an assistant-id-addressed HTTP surface** — so each app still stands up its own process. That distinction should be corrected in the PRD, because it changes the estimate materially: "8 days and 81 lines of code" is the legacy path's cost, not the SDK's.

## Part 2 — Where we agree, and where we push back

### Agree, strongly

- **Assistant as configuration, not code.** This is already the SDK's direction (`AssistantManifest` + `build_from_manifest` + `ProfileRegistry`), and the PRD gives it the missing product surface.
- **Skills as the only unit of work, shared across assistants.** Matches the tiered `SkillRegistry`.
- **APIs + auto-generated docs as the Phase-1 deliverable, measured by "a frontend dev builds a screen with no core engineering."** This is the best thing in the PRD: an unfakeable acceptance test. Keep it exactly as written.
- **Skill inherits IO from what it wraps rather than forcing one envelope.** Right instinct — see the qualification in pushback #4.
- **UAF is the RBAC checkpoint, not the record-keeper; run-time data access is platform user RBAC, not UAF's.** Correct, and consistent with `authority/`.
- **Framework carries no domain knowledge.** Correct, and already enforced by the pack boundary.
- **Task memory stays with the agents.** The code agrees (`spec.py:184` reserves `MemoryBinding`).
- **Approving feedback is out of scope; only human-approved feedback flows back.** Already exactly how `fabric/guidance/` works.

### Push back — four design conflicts

**1. Guardrails must not be skills. (Goal 8)**
The PRD is internally inconsistent here: it wants guardrails "plugged in as a skill" *and* "always on, no manifest can turn it off." In this codebase a skill is a **model-callable tool the router or the LLM chooses** — making guardrails skills makes them selectable and therefore skippable, which is the opposite of a floor. The SDK already models a guardrail correctly as `Guardrail(check, phase)` in a phase-aware, trust-tiered `GuardrailRegistry`, executed unconditionally *around* the turn in `agent.py:_run_guardrails` with typed refusals and boot-time phase validation.
*Counter-proposal:* keep the guardrail primitive; expose the extensibility the PRD actually wants by letting a `Guardrail.check` call a customer's guardrail agent — `registry.py:llm_guardrail` is already that shape. Then make the safety floor genuinely non-negotiable (today `spec.guardrails` defaults **empty**; only the scope guardrail is force-injected by `bind_spec`) and log every hit to the trace. Same outcome, no new skippable path. Note the naming trap this repo has already hit: `skills/governance/BaseGovernanceSkill` is a Governor-mode action class, unrelated to conversational guardrails.

**2. "One shared orchestrator; the only thing the builder picks is the LLM" understates what exists and will get overridden within a quarter. (Goal 6)**
The SDK has four orchestration layers with different owners: pluggable `Router` (skill pre-selection), `tool_use_behavior` (turn termination, per-parent and per-skill), the 13-mode `MODE_REGISTRY` with `ModeKind.ORCHESTRATOR`, and `conductor/` (pipeline, fanout, ensemble, replication, durable suspension) plus `agents/adjudication/pipeline.py`. `router.py`'s own docstring argues that presenting one routing policy as the only possibility is the mistake to avoid.
*Counter-proposal:* say **"one *default* orchestrator, and routing is a named registered policy"** — `default_llm` today, `intent_first` already built (which is the PRD's own Phase-2 "classifier-based routing", available now). Cost of getting this wrong: the PRD's phrasing invites a Phase-1 implementation that hardcodes the router and then has to be unpicked for the first CRE/AML assistant that needs deterministic routing.
*Also fix in the same goal:* the PRD says "every model call goes through the LLM Gateway." Today that is **half true**, which is worse than either extreme. The skill-less grounded path already delegates to `LLMManager` (`agents/service.py:218-256`, wired by `interactive/factory.py:36`); the **agentic/skills path bypasses it** through `build_agent`, and the `"gpt-5.2"` literal is hardcoded at three sites (`agent.py:578,897,915`) — including the *sub-agent* model, so putting only `_build_agentic` on the Gateway would leave every skill sub-agent off it. Either close the agentic path properly or stop claiming universality.

**3. "An assistant is one manifest" collapses a separation the SDK deliberately built — and the PRD's own manifest is missing the field that separation protects. (Goal 1)**
Today there are two artifacts on purpose: `AssistantManifest` is the **governance envelope** (pack binding, allowed_skills, action classes, `autonomy_level`, governance_profile_ref) and `InteractiveAgentSpec` is the **execution profile** (persona, model, knowledge, guardrails, compaction, router). `bind_spec` enforces one-way narrowing and **fails closed on widening** — "widening is a certification violation" — and its docstring states persona/model/knowledge/compaction are "profile concerns the manifest has no opinion on." The PRD's manifest puts persona and runtime knobs *in* the manifest, which means either two artifacts (so "an assistant is one config file" isn't literally true) or losing the narrowing guarantee.
Two further mismatches in the same goal: the PRD's binary `type` (conversational | non-conversational) has to land against **two existing orthogonal enums** — `ArchetypeType` (7 values) and `SurfaceType` (5, incl. `GATEWAY` deliberately excluded from defaults) — where conversationality is currently *derived* (`spec_binding._CONVERSATIONAL_SURFACES`) and gated on a `ConversationStore` being present. And the PRD omits `autonomy_level` entirely (deferred to "later phases"), yet it is **mandatory on every manifest today and load-bearing in `authority/`** — a UAF authoring form without it cannot produce a valid manifest.
*Counter-proposal:* adopt option 1 from `Japes_Enhancement_Backlog` P1 — **manifest is the governance envelope and *references* a profile; the UAF form authors both and presents one screen.** Add `name`/`description`/`type` to the manifest; make `autonomy_level` a visible field with a sane default; decide `type` as a derived view over `SurfaceType`, not a third enum. This P1 has been open since 2026-08-03 and is now on the critical path — **settle it before Builder Studio UI work starts**, because reworking the form after is more expensive than deciding first.

**4. "No forced IO shape" is right as a principle and wrong as an implementation instruction. (Goal 5/14)**
"A skill inherits its inputs and outputs from what it invokes" plus "no common IO shape" reads, in code, as *no schema at all* — and that contradicts Goal 14, which needs declared inputs/outputs per endpoint to generate APIs and docs. It also fights the SDK's typed-contract culture (`fabric/canonical/*`, `ModeContract.canonical_produces/consumes`, `PermissionScope` selectors). Meanwhile today's reality is the opposite extreme for two of the three shapes: def-backed skills (`as_tool`, `agent.py:658-666`) and `spec_ref` skills (`agent.py:785-793`) are both exposed as `(query: str) -> str`, so the SDK has a **forced string port** and no declared IO. Only a bare skill name resolving straight to a catalog callable keeps its native signature (`agent.py:667-671`) — which is, notably, the one shape that already does what the PRD wants.
*Counter-proposal:* the skill record carries a **JSON Schema for inputs and outputs, derived (and where possible auto-derived) from the wrapped agent/tool/process — not hand-authored, not templated**. That is what "inherits" should mean. It gives Goal 14 its docs generator and per-endpoint validation, keeps heterogeneous IO, and generalizes what `_build_parent_tools`' bare-name branch already does — real typed tool signatures — to the def-backed and `spec_ref` branches. Say this explicitly in the PRD, or it will be implemented as untyped passthrough and Goal 14 will be built on hand-written docs — the exact thing the PRD says it is replacing.

### Three smaller corrections

- **Out-of-scope handling (Goal 7) as written is weaker than the PRD believes.** The shipped default (`scope.py`) is substring matching on action-class words that **defaults to allow** when nothing matches, with the decline text hardcoded. The PRD's "a mortgage assistant never answers 'what's the weather'" needs the LLM variant (`registry.py:scope_guardrail`) or a description-driven check on the path, plus configurable message/tone/redirect. Also: keep it a *guardrail*, per pushback #1 — "out-of-scope handling is itself a skill" has the same skippability problem.
- **Three silent-degradation paths in `manifest/loader.py` should become deploy-time hard failures under Goal 1.** `resolve_pack` warns and returns `None` on a missing pack or an unsatisfied version range; worse, an **unparseable `pack_version_range` logs a warning and returns the pack anyway** (`except InvalidSpecifier` falls through to `return pack`). That is the sharpest "half-works silently" instance in the repo, and it sits directly under the PRD's own bar.
- **The PRD would be a regression in several places if its formats are taken as specs**, so specify these as *floors, not ceilings*: `CanonicalTrace`/`TraceStep` (per-step autonomy, override events, version bundles) vs. a flat interaction log; lossless archive/overlay compaction vs. "summarize behind the scenes"; resumable durable SSE with cooperative stop vs. "streaming on/off" (note `bind_spec` deliberately never defaults `stream`, which conflicts with the PRD's "on by default"); the governed guidance lifecycle (validation, conflict detection, expiry, provenance, A/B, effectiveness attribution) vs. "approved feedback as added context"; and `Skill.spec_ref` nested fully-guarded assistants vs. a flat skill model.

### Terminology — settle before Builder Studio ships a form

"Skill" currently means **five** things in this repo, and the PRD's definition matches **none** of them cleanly:

1. a scoped sub-agent definition (`agents/interactive/spec.py:26`; the example YAML says so verbatim);
2. a bare name resolving to a direct tool on the parent (`agent.py:_build_parent_tools` else-branch);
3. an entire assistant nested as a skill (`Skill.spec_ref`) — the only meaning that is genuinely a *wrapper*;
4. an ABC action-class contract layer (`skills/{evidence,governance,investigation}/base.py`; `experts/registry.py:222-239` errors explicitly that these "are Skill types, not Expert surfaces");
5. a markdown domain-knowledge file for a cognitive mode (`modes/prompt_loader.py:2-17`: "the term 'prompts' is deprecated… these files contain domain skills").

Plus: "memory" = conversation continuity here but both senses in the PRD; `session_id` vs `conversation_id` are distinct in `agent.py`/`runs/` (a conversation holds runs) and the PRD conflates them. Adopt the rule from the architect assessment — **the Canonical Object Schema Specification's vocabulary wins; anything else is a local implementation name that must not appear in a manifest** — and pick one owner for the word "skill" before the catalog is seeded, because after seeding it is a data migration.

### One question the PRD should answer before Phase 1 starts

**Who owns starting a process?** Goal 5 makes skill→process one of three first-class cases and "Fetch Loan Conditions" the async exemplar and the non-conversational proof (Goal 15). `japes` can only *read* Flowable (`tools/platform/workflow.py`); no code anywhere in the SDK starts a process instance. Until Kernel or a new client owns this, Goal 5 is two-thirds deliverable and the Goal 15 non-conversational proof has no backend.
