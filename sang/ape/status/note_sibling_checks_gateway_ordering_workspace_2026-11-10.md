## 1. Our gateway agent path against macer's `GatewayAnthropicModel`

| Item | Result |

Breakpoint rule: ours is `cache_breakpoint_indices` (last message, the turn before each of the last two user turns, plus the system prompt), the rule of the native path, shared since 034e45f0; macer's is `macer.models.anthropic._transform_messages_for_cache`, its own direct-path rule, not compared line by line `[U]`. |

## 2. `processing_pipeline` defaults and `latest` ordering: japes call sites

What japes passes: nothing. `processing_pipeline` appears in japes only as the name of our own document-processing pipeline; no Knowledge Hub call forwards it. The generated calls at our pin accept it (`read_entities`, `list_documents`: `processing_pipeline`, and `latest` defaulting to `True` on `read_entities`), but the facade (`clients/knowledge_hub_client.py` `read_entities`, `read_entities_v2`, `list_documents`) never passes `processing_pipeline` or `latest`, and passes `orderby` only when a caller gives one `[V]`.

Consequence of knowledge_hub's new default (no `processing_pipeline` means every row, tagged or not): every listing below sees any rows another writer tagged with a processing pipeline that it did not see before, if the filter was on where those ran; japes itself writes none, so the change shows only against a collection a Knowledge Hub pipeline also writes to `[U: which deployments have tagged rows]`.

| Call site | Lists | Order or latest reliance | Sees more rows? |
|---|---|---|---|
| `fabric/canonical/store/_base.py:140` `get`, `core.py:150` `get_policy` | entities by `name eq` and type | takes `entities[0]`: relies on `latest=True` (the default) returning one row per name; MA-4692 makes that SQL `DISTINCT ON (name)` and fine | tagged duplicates of a name could now come back; `latest` still collapses them to one, which row is the latest per name is the hub's |
| `_base.py:159` `list`, `core.py:197` `list_policies` (pages of 500 with `skip`) | entities of a type | no `orderby`: paging needs a stable order; MA-4692 orders by id when none is given, which makes these pages stable (better than before) | yes, tagged rows |
| `fabric/entities/store.py:165` `_find_by_fingerprint` | entities by name, `limit=500`, then picks the first in this collection | relies on first match; `latest` is per name, so a name held in two collections returns only the latest one and the other collection's row is invisible (a pre-existing limit, not new) | yes |
| `fabric/entities/store.py:248` `list` | entities, caller's `orderby` | the caller's order; with MA-4692 `orderby` sorts natively, not as strings: a change for numeric or date order keys | yes |
| `fabric/canonical/store/facade.py:188` `filter_entities` | filtered entities, `orderby` and direction | explicit order | `filter_entities` takes no `processing_pipeline` at our pin `[V]`; unaffected |
| `fabric/docs/store.py:511` `_find_by_hash` (page 1000) and `:1329` collection sync, `tools/knowledge_hub/documents.py:89,256` (name lookup, pages of 1000), `mcp/knowledge_hub_tools.py:151`, `fabric/docs/store.py:1441,1452` | documents | no `orderby`; the name lookup returns the first document with the name, so it relies on an order no one set (MA-4692 is about entity listings, not documents `[U]`) | yes, tagged documents (derived or processed ones) |
| `mcp/knowledge_hub_tools.py:51` | entities, caller's `odata_query` | none | yes |

Flags: (1) the two collection scans that decide dedupe and sync (`_find_by_hash`, collection sync) and the name lookup in `tools/knowledge_hub/documents.py` would be safest with an explicit `processing_pipeline` of the writer they mean (or the facade forwarding the argument so a caller can say) and an explicit `orderby`; today they cannot say either, because the facade has no parameter for it. (2) `core.list_policies` and `_base.list` should pass `orderby` (id or name) so paging does not depend on the hub's default. (3) `_find_by_fingerprint` should filter by `collection_id` server-side if `latest` per name is not per collection `[U]`. No change made; adding `processing_pipeline` and `latest` pass-throughs to `read_entities`, `read_entities_v2` and `list_documents` (and both mocks) is the small first step.

## 3. Kernel `discardWorkspace`

- **What exists:** nothing. `KernelClient` and `clients/kernel_admin.py` (agents, tools, llms, notepads, chat, config namespaces) have no workspace method, and `kernel_admin_types.py` and `kernel_invoke.py` mention no workspace [V grep, "workspace" and "discard" found nowhere in the four kernel client modules].
- **What the generated client offers:** nothing yet. The route is in kernel's OpenAPI (`240de25b`, `DELETE /api/v1/workspaces/{workspace_id}`, operation `discardWorkspace`, 200 with a free-form object, 422), but client-api's `kernel-client` on `origin/main` has no `workspaces` group (its api groups: agents, chat, collections, feedback, knowledge_hub, llm, mcp_client, notepads, status, stream) and no regeneration since the route was added is in the refs I have `[V local refs, not fetched]`.
- **What the route is:** "Deletes every kernel row of the workspace (agent, tool and LLM copies and tombstones, invocations and other runtime data). Base data is never touched. Called by Builder Studio when a shared workspace is merged or deleted; must be called without workspace context. Only Builder Studio's service token (X-Actor-Token) is accepted." So the caller is Builder Studio's service, with its own token, and the call must carry no workspace (sub-tenant) context.
- **Should there be a method:** that is the host-declared workspace claim decision. What bears on it: a japes-based caller can only use it with the service token and no workspace context, which the client's `request_headers_provider` would have to supply or withhold (it forwards the inbound caller's headers on every request by default); a method that silently forwards a workspace claim would be refused by the server. And it is destructive over every kernel row of a workspace, the same class as the bulk-delete facade (typed result, raise on a 5xx since kernel's own note says a 5xx after a delete may follow a completed delete, no automatic retry). Missing today: the generated binding (needs the regeneration in client-api first), then a method on a `workspaces` namespace in `kernel_admin.py`.
