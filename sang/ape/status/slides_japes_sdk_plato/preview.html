Japes SDK and Plato

02

The services built before japes are v1-shaped: each one solved LLM calls, tracing, knowledge access and governance its own way. Japes takes the patterns those services proved and makes them the one consistent default. Plato goes a step further: for many apps there is no new service at all, only a pack published to Plato.

Japes SDK and Plato

04

Read it top down. A pipeline is a declared sequence of steps the Conductor executes, with loops, streaming and durable resume. Pipelines wire platform agents, which are task-specific agents configured as data. Those run through the agent execution layer, which handles provider routing, tracing and cost. Everything reads and writes through the knowledge fabric. The runtime at the bottom is the queue and service plumbing.

06

Every route sits under /api/v1, like the sibling services. Plato keeps its own Postgres control plane for assistant configuration, the pack store, runs, feedback and evaluation. The boot contract is one table that decides what each misconfiguration does: a serving replica comes up and reports, a job exits on a documented code.

Japes SDK and Plato

09

The next four slides take these stages in turn. The ordering is deliberate: a pack is crafted and proved on gold cases before it sees a real transaction. The methodology comes from the domain pack quickstart and is how jaci's reference packs were built.

01 · Craft

Design the pack before running a transaction

  1. Find the policies and author them as canonical Policy objects
  2. Find the playbooks: how experts actually work a case
  3. Design the ontology: the domain's entities and relations
  4. Design the workflow: the dominant loop and its side checks
  5. Specialize the modes by tuning, not by writing new code

THE SDK SUPPLIES

A policy expert configured with the pack's policies, no subclass needed

Thirteen cognition modes, tuned per pack with markdown

A Conductor that runs the declared workflow, so no pack hand-writes orchestration

Japes SDK and Plato

10

Crafting is design-first. The team's work is domain knowledge: what the rules are, how an expert works a case, what the entities are. The SDK supplies the machinery: the policy expert is configured rather than subclassed, the modes (investigator, verifier, reasoner, governor, narrator and others) are tuned with markdown, and the Conductor runs the workflow.

02 · Prove

The pack earns live work on gold cases

Gold cases

Typed inputs with expected results, written before tuning. The harness runs each end to end against a pass threshold the pack declares.

Deterministic assessment

Every rule checked against a record, the binding rule named, one attestation per rule. No model involved.

Formal checks

Z3 checks compiled from the same canonical policy, one attestation per claim. Local today; deployed once an isolated job service is in place.

Proof comes from the policy itself, not from asking a model whether it complied.

Japes SDK and Plato

11

Three kinds of evidence. Gold cases measure the pack end to end. The deterministic assessment evaluates every policy rule against a record with no model in the loop. Formal checks compile the same canonical policy into Z3 claims. Be precise about formal checks: they run locally today, and deployed Plato refuses them until an isolated job service is configured.

Japes SDK and Plato

12

Publishing runs the same check a team can call ahead of time, and refuses a pack with blocking findings, such as a missing skill or a guardrail nothing registers. Activation is a per-tenant pin, so tenants move to a new version independently. A run started on one version finishes on it.

05 · Improve

Feedback becomes a measured change

1

A user or reviewer submits feedback on an answer

2

It is processed, reviewed, and added to a dataset

3

An experiment measures a change against a baseline

4

The winning prompt is applied to the pack draft

Nothing publishes itself. An optimization lands in the draft; a person publishes the next version.

Japes SDK and Plato

13

This is the compounding loop. Feedback on a hosted assistant is submitted, processed, reviewed, and can be added to an evaluation dataset as a case. Experiments compare a change against a baseline. Prompt optimization picks a winner and applies it to the tenant's pack draft on request. It never publishes: the next version goes out through the same check and publish path as the first.
